# 《同行计划》共享样例和状态约定

依据修订版 A/B/C 第一周任务书、`origin/main` 中的共享样例和 B 的检测器，以及 A 的[周二交接记录](trip-state-handoff.md)。下文给出当前分支的联调约定，供 B/C 复核。HTTP 请求与响应集中在 [API 契约](api-contract.md)，v0.1 待团队复核。

| 决定 | 当前约定 |
| --- | --- |
| 演示任务边界 | 第一周分开验收 Android 真机断网的单机四身份流程与 Python 本地硬约束、行程状态及变更。第二周由 A 提供 FastAPI 共用服务，C 接 Android 房间流程，验证四机独立身份入房、提交及一致汇总。 |
| 共享样例 | [源 JSON](../fixtures/demo-trip.json) 为固定输入。Android 将源样例同步到 `mobile/assets/demo-trip.json` 后打包，以文件内容校验一致性。Python 直接读取源文件并运行 B 的检测器，Android 离线用同一批 ID 对照固定展示结果。 |
| 分工 | A 实现状态、雨窗命中和预览后的版本提交。B 负责候选与替代后全程的硬约束检测。C 维护共享样例、Flutter Android 页面和 APK。D 核对预算口径与研究证据。 |
| 演示权限 | `m01` 是发起人。选案、开始、发起预览、取消及批准变更由发起人操作，四名成员各自提交和确认原候选。变更批准权限是演示约定，联机权限策略由 B/C 与 A 复核。 |

## ID、单位与版本

| 概念 | 字段和值 | 使用约定 |
| --- | --- | --- |
| 成员 | `member_id` 为 `m01`、`m02`、`m03`、`m04` | 显示名依次为甲、乙、丙、丁。Android 单机可在固定身份间切换，独立保存各人提交和确认。联机由服务端身份决定谁可提交与确认。 |
| 候选 | `candidate_id` 为 `c01`、`c02`、`c03` | C 用 ID 对应 B 的判定和卡片。执行中局部替换保留 `c02`，以计划版本区分变更前后。 |
| 节点 | `node_id` 以 `c02-n01` 至 `c02-n04` 为例 | 按行程顺序展示。合成的室内替代是 `c02-n02-r1`，通过 `rain_replacement.replaces` 关联 `c02-n02`。 |
| 计划版本 | `PlanRef(candidate_id, version)`，`version` 形如 `v1`、`v2` | 首次选定生成 `v1`，改选新候选或批准变更生成递增版本。确认绑定成员、候选及版本。预览查询当前版本，确认不得跨版本应用。 |
| 样例及判定版本 | `fixture_version`、`input_fingerprint` | 共享样例 1.1 加入降雨事件和替代。B 的结果保留样例版本和输入指纹供联调追踪。确认与校验过期的依据是当前计划状态和版本。 |
| 时间 | `Asia/Shanghai`，接口值用带偏移的 ISO 8601，例如 `2026-11-21T14:00:00+08:00` | 成员可有多个可用窗。B 先合并个人重叠或相邻窗口，再取四人正时长交集。候选全程含出发及返校。共享样例的共同窗为 13:30–17:00。 |
| 金额 | 人民币整数分，`budget_cap`、`cost_per_member` | 演示为逐人承担，含往返交通，`budget_basis.scope = per_person`。等于上限通过，超限按成员解释。界面换算为元展示。 |
| 模拟来源 | `source.type = simulated`，含 `note` 与 `retrieved_at` | 固定候选和降雨均保留来源及时间。天气、路线、营业或费用展示模拟标记。 |

## 给 C 的状态与按钮

| `phase` | 成员可用动作 | 发起人额外可用动作与门槛 | 页面反馈 |
| --- | --- | --- | --- |
| `collecting` | 提交或更新自己资料 | `pending_member_ids` 为空才启用发布候选 | 群组与偏好页显示已提交和待提交成员。 |
| `candidates` | 比较三张卡，展开失败原因或待补字段 | 可选择 `feasible` 候选，或返回填报 | `c01` 显示 `m01` 超预算 ¥1，禁用选择。都被拦时提示补填或修改。 |
| `confirming`，未锁定 | 确认选中的候选和版本，已确认者可查看记录 | 可改选或返回填报，开始按钮禁用 | 展示 `selected_plan` 与 `confirmed_member_ids` 对应的进度。改选清空旧确认。 |
| `confirming`，已锁定 | 查看 4/4 及确认记录 | 可开始当前 `locked_plan`，开始前可改选或返回填报 | 版本落后时刷新后查看。 |
| `executing` | 查看当前行程及记录 | 可触发模拟降雨；查看模拟导出或通知 | 显示当前版本，区分原候选四次确认与之后的变更批准。 |
| `change_pending` | 查看受影响节点、保留节点、理由和替代 | 当前有效预览可取消或确认，操作使用 `preview_id` 和基线版本 | 取消回到原计划；版本已变则提示按当前版本重新预览；无权限或预览失效显示原因。 |

原候选确认四人各占一条记录。重复确认同版本只计一次。改选、返回填报或应用变更后，旧确认以原版本留在历史中。应用变更的确认人和时间记录在独立事件中，界面展示发起人批准。状态事件使用事件名、前后状态、操作者、时间、候选和计划版本，拒绝时带原因。

## 给 B 的候选判定与复检

发起人发布时，A 调用 `open_fixture_candidates(fixture, actor_id=...)`，使用已提交的成员资料和候选池对每张卡运行 `algorithm.conflict_detector.detect(fixture, candidate_id)`。A 保存候选和检测输入的快照供执行与复检。候选可选性只看 `status` 的已知取值。返回填报后，按更新后的资料重新检测并发布。

| `status` | 含义与呈现 |
| --- | --- |
| `feasible` | 通过 B 当前硬约束规则，可进入确认。固定样例为 `c02` 和 `c03`。 |
| `infeasible` | 违反硬约束，卡片可查看、不可选择。保留 `reasons` 的 `rule_id`、`member_ids`、`field`、`message`，若有 `actual`、`threshold` 一并保留。`c01` 的 `R-BUD-01` 为 `m01` 实际 8100 分、上限 8000 分。 |
| `incomplete` | 字段缺失、格式非法或预算口径未定。保留 `missing_fields` 中的 `member_id`、`field`、`rule_id`，提示补填。 |

变更输入固定在样例顶层。`rain_event` 包含 `event_id = rain-01`、`type = rain`、`window` 和 `source`，固定雨窗为 11 月 21 日 14:00–15:00，`source.retrieved_at` 为当日 13:45。活动节点的 `indoor: false` 表示户外。对明确为户外的活动检查 `max(节点开始, 雨窗开始) < min(节点结束, 雨窗结束)`。受影响 `c02-n02`，保留顺序为 `c02-n01`、`c02-n03`、`c02-n04`。

`rain_replacement` 提供 `replaces`、新 `node` 及完整的 `cost_per_member`。样例只替换 `c02-n02`，新节点 `c02-n02-r1` 同时段、`indoor: true`，每人承担 6400 分。A 展开当前行程，将 `candidate_id`、更新后的全程 `window`、逐人金额和完整 `nodes` 一起交 `algorithm.conflict_detector.detect_resolved(fixture, trip)`。只有 `feasible` 生成可确认预览。

变更结果提供 `affected_node_ids`、`unchanged_node_ids`、`replacement`、`reason`、`rule_result`、`rain_event`。可行预览关联一个 `preview_id` 与当前计划版本。应用时校验发起人、活动中的预览和基线版本，仅替换目标节点并记录新版本。取消、无替代、复检失败和过期操作均保留最近确认版本；过期后用当前行程重新预览。

## 联调复核

| 复核人 | 核对项 |
| --- | --- |
| B | 以共享样例单独跑候选检测，确认 `c01` 唯一预算冲突。核对对 `c02` 替代后的完整行程复用原硬约束，并复验时间、预算等失败反馈。 |
| C | 对照 Android 和 Python 的 `m01`、`c01`、`c02` 及替换节点 ID。逐一走查四个身份和按钮权限、取消及确认，真机安装证据填入演示记录。 |
